# Cocoa 互操作手册

> 适用范围：native DLL、.NET DLL、`.cod` 程序集三类互操作
> 状态：native DLL（Native 路径 6c-1 + IL 路径 managed P/Invoke 5-3 ~ 5-5；**import 块强制类内 6e-M17 Step 4 + extern 元数据（entry/charset）Step 5**）已落地；.NET DLL 消费（`-r` + `using`，M4）已落地；`.cod`（Cocoa 程序集）设计中（阶段 6b）
> 最后更新：2026-08-22

---

## 1. 总览

| 目标 | 语法 | 机制 | 平台路径 | 阶段 |
|------|------|------|---------|------|
| native DLL | `import kernel32.dll { static extern ... }`（类内 import 块，6e-M17 Step 4） | 导入表 + 启动 stub 模块走查 → LLA 回退（Native 6c-1 已落地）/ ImplMap（IL 路径已落地 5-5） | Native + IL | 6 |
| `.cod` 程序集 | `-r a.cod` / `[references]` + `using MyLib` | 编译期语义层（BoundProgram）合并 + 公共符号表并入 Binder（等价 .NET dll 语义，无入口点，`requires` 后端校验） | Native + IL | 6b |
| .NET DLL | `-r mylib.dll` + `using MyLib` | AssemblyRef 直通 + Binder 读引用程序集 public 类型（M4 已落地） | 仅 IL | 6 |
| .NET（Native） | — | CLR Hosting | 仅 Native | 9（可选） |

**统一原则**：dll 与 native DLL 的消费统一走 **import 导入表**机制；`.cod` 是编译期合并机制（无 ABI 风险），与运行期机制分离；`.cod` 与 .NET dll 的消费体验一致（`-r` + `using`）。

**`.cod` 中间库性质**：`.cod` 是**语义层程序集**（BoundProgram 序列化，后端无关），**一次编译、多端消费**——不按后端/平台区分编译；后端差异（导入表 vs ImplMap、x86/x64）全部在消费端发射时解决；存在的"区分"仅三种机制：格式版本校验（v1/v2）、`requires` 消费端校验门（any/dotnet）、平台导入清单记录。详见 `docs/标准库设计.md` §7。

## 2. native DLL 导入

### 2.1 语法（6e-M17 Step 4：import 块强制类内）

```cocoa
class Kernel32
{
    import kernel32.dll
    {
        static stdcall function GetStdHandle(nStdHandle: int): int
    }
}

function Main()
{
    let h = Kernel32.GetStdHandle(-11)      // 类名限定调用
    System.Console.WriteLine("hello")
}
```

coproj 中声明（`[imports]` 节解析但构建仅警告，实际声明走源码 import 块）：

```
[imports]
kernel32.dll
user32.dll
```

### 2.2 机制（Native 路径，阶段 6c-2 已落地）

1. `import` 的每个 DLL 生成一组导入描述符 + IAT（`.idata` 基础设施，`PeImportTable` 多组复用，`PeImportTable` 按 DLL 分组）
2. **OS 加载器静态解析**（6c-2 起，自研解析 stub 已删除）：
   - 描述符 `FirstThunk` 直接指向**镜像内 data 区的 IAT 槽数组**（单一 IAT，无 blob 内副本），数据区槽磁盘初值为各函数的 **hintname RVA**（mingw fake-IAT 惯例）——Windows 加载器对初值为 0 的槽视为已填充而跳过，只有指向 INT 区域的"伪值"才会在启动时被替换为解析后的真实函数地址
   - 进程入口即用户入口（`main`），加载器完成导入填充后直接进入
3. `import` 的名字解析到 IAT 槽，程序直接调用
4. 未知符号 → 编译期诊断错误（`NativeImportValidator`）

**已验证能力**（e2e，`NativeImportE2eTests` 8 测试全绿）：kernel32 直取、user32 跨 DLL（MessageBeep）、跨 DLL 多参数穿越（GetTickCount + MessageBeep 组合）、x86/x64 双平台、程序集名含点号（`kernel32.dll` 多段 token）。x64/x86 双平台均适用（槽宽度 8/4 字节）。

**管道输出契约**：Native 程序经管道交互时，stdout 输出为 **UTF-16 原始字节**（非 UTF-8）；测试 harness 与外部脚本必须按 `Encoding.Unicode` 解码。

### 2.3 调用约定（Native）

| 平台 | 约定 | 说明 |
|------|------|------|
| x86 | `cdecl`（默认）/ `stdcall` | 导入函数声明可标注 |
| x64 | 单一约定（Windows x64 统一） | 无需标注 |

```cocoa
class User32
{
    import user32.dll
    {
        static cdecl function MessageBoxA(hWnd: int, text: int, caption: int, type: int): int
    }
}
```

### 2.4 与 `export` 的关系

- 本编译器 `-f dll` 导出（`export fn`）→ 其他 Cocoa 程序/其他语言程序 `import` 消费
- 同一导入表机制，双向闭环

### 2.5 IL 路径：managed P/Invoke（阶段 5-3 ~ 5-5 已落地，双机制共享同一语法）

IL 路径（托管 PE 输出）消费 native DLL 走 **ImplMap/ModuleRef** 机制（ECMA-335 II.15），不产生导入表/IAT：

```cocoa
class Kernel32
{
    import kernel32.dll
    {
        static stdcall function GetTickCount(): int
        static stdcall function ExitProcess(exitCode: int)
    }
}

function Main()
{
    var t = Kernel32.GetTickCount()
    Kernel32.ExitProcess(42)          // 参数/返回值穿越 P/Invoke 桩
}
```

**语法规则**（6e-M17 Step 4 起；extern 元数据 Step 5 落地）：
- `import <dll 名> { ... }`：**只作类成员**（import 块），点号分隔的文件名，`DllName` 由 token 拼接；DLL 归属由块声明式绑定
- 块内成员只允许 `static` extern 函数声明：`static cdecl` / `static stdcall` 修饰的 `function` → **外部函数声明**（允许无函数体；带函数体 → 诊断错误）
- extern 强制 `static`（对齐 C# `static extern`）
- **顶层位置式 `import` / extern 已废弃**（诊断错误，强制迁移到类内 import 块）
- **extern 元数据**（Step 5）：`extern(entry = MessageBoxA, charset = ansi)` 括号可选、命名键值、逗号分隔——`entry` 映射 DLL 导出名别名（缺省 = 函数名）、`charset` 编码（缺省 = 块级/unicode）；块级键 `import user32.dll charset = unicode` 设置块内函数缺省编码；未知键/值 → 诊断错误
- 无修饰的 `function` 声明不变（普通函数，函数体必填）

**写侧机制**（自研元数据写入器）：
- extern 方法：MethodDef 的 Flags 含 PInvokeImpl(0x2000)、RVA = 0；ImplFlags = PreserveSig(0x0080)
- ModuleRef 表：每个 `import` 一行（按首见顺序去重）
- ImplMap 表：MappingFlags = 约定掩码 | CharSet 位（Winapi 0x0100 / Cdecl 0x0200 / StdCall 0x0300；**CharSetUnicode 0x0004 缺省**，Ansi 0x0002 / Auto 0x0006）；ImportName = `entry ?? 函数名`；MemberForwarded 指向该方法
- **IL 签名恒用默认调用约定（首字节 0x00）**，本机约定只由 ImplMap.MappingFlags 表达

**已验证能力**（e2e，`dotnet` 运行验证）：
- 零参（GetTickCount → int 返回值）、带参（ExitProcess(int) → 退出码验证参数穿越）、int→指针（`GetModuleHandleW(0)` → LPWSTR NULL）、stdcall/cdecl 双关键字、**entry 别名**（`extern(entry = ExitProcess)` → 退出码 42 验证别名解析）、charset=ansi IL Ansi 位
- native 路径：entry 别名 e2e（导入表按别名解析）+ 遇 `charset = ansi` 编译期报"未实现"（native 仅支持 unicode）

**当前限制**（阶段 6 语言扩展前置）：
- 参数/返回类型仅限 int/bool/void（`GetStdHandle(-11)` 等 int 参数 API 可直接用）
- 字符串参数需 LPStr/UTF 编组（`byte[]` + 字符串增强后支持）；`MessageBoxA(hWnd, text, caption, type)` 待字符串编组落地

### 2.6 类型映射（托管 ↔ 非托管，统一 ABI）

Cocoa 类型跨三后端（Evaluator/IL/native）的统一表示（对齐 .NET P/Invoke 编组表，详见 `docs/标准库设计.md` §3）：

| Cocoa 类型 | Evaluator（C#） | IL（.NET） | native（Windows） | 编组类别 |
|-----------|----------------|-----------|-------------------|---------|
| `int` | `int` | `System.Int32` | 4B dword | blittable 直通 |
| `byte` | `byte` | `System.Byte` | 1B | blittable 直通 |
| `bool` | `bool` | `System.Boolean` | 4B 0/1（BOOL 语义） | 非 blittable（扩展 4B） |
| `char` | `char` | `System.Char`（2B UTF-16） | 2B UTF-16 | 非 blittable |
| `double` | `double` | `System.Double` | 8B（SSE） | blittable 直通 |
| `string` | `string` | `System.String` | `[len:4][UTF-16 chars]` | 非 blittable |
| `T[]` | `T[]` | `System.T[]` | `[len:4][elements]` | 非 blittable（参数 pin） |

**extern 穿越编组规则**（当前仅 int/bool/void，string/数组留扩展位）：
- **blittable 直通**（int/byte/double/指针）：内存布局一致，零转换——native 侧即"零编组"（对应 .NET 7+ `DisableRuntimeMarshalling`）。
- **bool**：4 字节 0/1（Win32 `BOOL` 语义），IL 侧 P/Invoke 由 CLR 编组桩转换。
- **string 编组（扩展位）**：native string 为 `[len][UTF-16]`，与 `WriteConsoleW`/`MessageBoxW` 的 `LPWSTR` 天然一致——穿越时跳过长度头传 UTF-16 缓冲（对应 .NET `CharSet.Unicode`）。import 块（`class User32 { import user32.dll { static stdcall function MessageBoxW(hWnd: int, text: string, caption: string, type: int): int } }`）即闭环。
- **数组（扩展位）**：参数指向元素首地址（native 需跳过 4B 长度头），对应 .NET 数组 pin。
- 调用约定：x86 标注 `cdecl`/`stdcall`（`ImplMap.MappingFlags`：Winapi=0x0100/Cdecl=0x0200/StdCall=0x0300）；x64 单一约定。

**与 .NET Console 分层的对照**：native 运行时与 .NET `ConsolePal` 调同一批 kernel32 API（`WriteConsoleW`/`WriteFile`/`ReadConsoleW`/`ReadConsoleInputW`/`GetCommandLineW`/`GetStdHandle`）；我们的功能层原语（`System.Runtime.WriteLine`/`ReadLine`/`Random` 等，6e-M17 syscall 声明）即 `Interop.Kernel32` 式的集中声明 + per-backend 实现。

## 3. `.cod` 程序集消费

`.cod` 是 Cocoa 的"程序集"（等价 .NET dll）：每库一个/多个 `namespace`、无入口点、公共符号表（public 类型/函数/枚举/全局变量）按命名空间组织。消费体验与 .NET dll 一致：

```cocoa
// lib.cod 由 cocoa build -p lib.coproj -f cocoa 生成（源码含 namespace MyLib）
// 消费方 coproj:
[references]
../Libs/lib.cod
```

也可直接引用库项目（自动递归构建 + 产物复制到当前生成目录，等价引用其 `.cod`）：

```cocoa
[references]
../Libs/lib.coproj   // output = cocoa → 构建后产物 lib.cod 复制到当前生成目录
```

```cocoa
using MyLib

function Main()
{
    let x = MyLib.Add(1, 2)     // 全限定调用
    let y = Add(1, 2)           // using 后非限定调用
}
```

- 加载 `.cod` → 反序列化**语义层 `BoundProgram`**（降级绑定树）+ 公共符号表 → 符号并入 Binder 作用域（按命名空间隔离）→ `using MyLib` 解析类型/函数/枚举/全局变量 → 消费方绑定完成后与 `.cod` 的 `BoundProgram` 片段**合并**（`docs/IR设计.md` §7）
- 无入口点校验：`output = cocoa` 项目禁止 `Main`，源码须含 `namespace`
- 符号冲突检测（同名导出 → 错误）
- 平台不匹配 → 错误（`.cod` 依赖清单含平台信息）

### 3.0 backend 约束（`requires`）

`.cod` 依赖清单声明 backend 要求，消费方编译期校验、不匹配报错：

| 库内容 | `requires` | native 消费 | IL 消费 |
|--------|-----------|------------|---------|
| 纯函数 + 基础类型（无外部依赖） | `any` | ✅ | ✅ |
| 含 native import（`import kernel32.dll`） | 平台绑定（双后端） | ✅ 导入表 | ✅ ImplMap |
| 含 .NET API（`System.Xxx`） | `dotnet` | ❌ 编译期报错（阶段 9 前） | ✅ |
| 含 OOP（class 实例化/继承/GC 对象） | `dotnet`（native 对象模型后置） | ❌ 编译期报错 | ✅ |

### 3.1 依赖传递

`.cod` 头部含**依赖清单**（.NET 程序集引用 + native 导入列表 + 被引用的 `.cod`，见 `docs/项目格式规范.md` §4.1）。消费方加载 `.cod` 时：

1. 反序列化 `BoundProgram` 与公共符号表
2. 读取依赖清单，校验 backend（`requires`）与平台
3. .NET 程序集引用 → 并入消费方引用集（IL 路径 AssemblyRef）
4. native 导入 → 合并 `import` 声明（→ 导入表）
5. 被引用的 `.cod` → **递归加载**（防环 + 去重，同一 `.cod` 间接引用只加载一次）

### 3.2 与 .NET 混用

导入 `.cod` 可以编译成 .NET 程序（IL 路径），因为语义层 `BoundProgram` 的符号可引用 .NET 元数据，cod 代码与 .NET 程序集引用在同一次编译中并存：

```
foo.cod（语义层，内部可引用 .NET API）
    │ [references] 加载 + 依赖传递 + requires 校验
    ▼
消费方编译单元 ──► IL 后端（IlEmitter）──► 托管 PE（.NET 程序）
                └──► Native 后端（BoundTreeToIr）──► 原生 PE（Windows）/ ELF（Linux，规划中）
```

| 消费方产物 | `.cod` 要求 | 结果 |
|-----------|------------|------|
| `-f exe`（IL 路径，netcore） | 任意 | .NET 托管程序（原生 apphost `x.exe` 直接运行 / `dotnet x.dll`） |
| `-f exe`（IL 路径，netfx `--dotnet-runtime net4x`） | 任意 | .NET Framework 托管程序（Windows 直接运行 `x.exe`，无需 dotnet 前缀） |
| `-f dll`（IL 路径） | 任意 | .NET 库，可被其他 .NET 程序引用 |
| `-f exe`（Native，纯 Cocoa 代码） | `any` 或含 native import | 原生 PE |
| Native 消费含 .NET API 的 `.cod` | `dotnet` | ❌ 编译期报错（需阶段 9 CLR Hosting） |

**边界**：Cocoa 泛型是编译期特化，cod 中已特化的泛型可引用 .NET 泛型类型；.NET 运行期泛型元数据无法反向进入语义层。跨 `.cod` 的泛型实例化需泛型体随代码区携带（阶段 6b 定稿时细化）。

## 4. .NET DLL 导入（IL 路径）

```cocoa
// 编译：cocoa main.co -r System.Runtime.dll
System.Console.WriteLine("hello")
System.Math.Max(10, 20)
```

### 4.1 机制

- IL 路径：`AssemblyRef` 直通（阶段 5 自研元数据写入器支持 AssemblyRef 表）
- 类型映射：`System.Xxx` → 元数据引用；Cocoa 基础类型映射到 CLR 类型
- 解析与重载：当前 Mono.Cecil 的 MetadataResolver 在阶段 5 重写为自研元数据读取

### 4.2 边界（阶段 6 范围）

| 能力 | 状态 |
|------|------|
| 静态方法调用 `call` | 阶段 6 |
| 实例方法调用 `callvirt` / 属性访问 | 阶段 6（语言扩展后） |
| 对象创建 `newobj` | 阶段 6（record/类支持后） |
| 泛型类型 | 阶段 6 |
| 异常 try/catch | 阶段 6 |

### 4.3 Native 路径的 .NET 互操作（阶段 9 可选）

- 通过 CLR Hosting API（`ICLRRuntimeHost` 等）在 Native 进程内加载 .NET 运行时并调用
- 纯 Windows 原生互操作，无第三方依赖
- 前置：阶段 6 的 native DLL 导入（Hosting API 本身就是 native API）
