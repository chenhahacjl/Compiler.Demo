# Cocoa 互操作手册

> 适用范围：native DLL、.NET DLL、`.cod` 库三类互操作
> 状态：设计中（阶段 6c）；native DLL（Native 路径 6c-1 已落地）+ IL 路径 managed P/Invoke（5-3 ~ 5-5）已落地；`.cod`/`.NET` 设计中
> 最后更新：2026-08-16

---

## 1. 总览

| 目标 | 语法 | 机制 | 平台路径 | 阶段 |
|------|------|------|---------|------|
| native DLL | `import kernel32.dll` | 导入表 + 启动 stub 模块走查 → LLA 回退（Native 6c-1 已落地）/ ImplMap（IL 路径已落地 5-5） | Native + IL | 6 |
| `.cod` 库 | `[references]` / `-r` | 编译期 IR 合并 | Native + IL | 6 |
| .NET DLL | `-r System.Runtime.dll` 等 | AssemblyRef 直通 | 仅 IL | 6 |
| .NET（Native） | — | CLR Hosting | 仅 Native | 9（可选） |

**统一原则**：dll 与 native DLL 的消费统一走 **import 导入表**机制；`.cod` 是编译期机制，与运行期机制分离。

## 2. native DLL 导入

### 2.1 语法

```cocoa
import kernel32.dll

function Main()
{
    let h = GetStdHandle(-11)        // 导入表中的函数直接可调
    print("hello")
}
```

coproj 中声明：

```
[imports]
kernel32.dll
user32.dll
```

### 2.2 机制（Native 路径，阶段 6c-2 已落地）

1. `import` 的每个 DLL 生成一组导入描述符 + IAT（`.idata` 基础设施，`PeImportTable` 多组复用，`PeImportTable` 按 DLL 分组）
2. **OS 加载器静态解析**（6c-2 起，自研解析 stub 已删除）：
   - 描述符 `FirstThunk` 直接指向**镜像内 data 区的 IAT 槽数组**（单一 IAT，无 blob 内副本），数据区槽磁盘初值为各函数的 **hintname RVA**（mingw fake-IAT 惯例）——Windows 加载器对初值为 0 的槽视为已填充而跳过，只有指向 INT 区域的"伪值"才会在启动时被替换为解析后的真实函数地址
   - 进程入口即用户入口（`main`），加载器完成导入填充后直接进入
3. `import` 的名字解析到 IAT 槽，程序直接调用
4. 未知符号 → 编译期诊断错误（`NativeImportValidator`）

**已验证能力**（e2e，`NativeImportE2eTests` 8 测试全绿）：kernel32 直取、user32 跨 DLL（MessageBeep）、跨 DLL 多参数穿越（GetTickCount + MessageBeep 组合）、x86/x64 双平台、程序集名含点号（`kernel32.dll` 多段 token）。x64/x86 双平台均适用（槽宽度 8/4 字节）。

**管道输出契约**：Native 程序经管道交互时，stdout 输出为 **UTF-16 原始字节**（非 UTF-8）；测试 harness 与外部脚本必须按 `Encoding.Unicode` 解码。

### 2.3 调用约定（Native）

| 平台 | 约定 | 说明 |
|------|------|------|
| x86 | `cdecl`（默认）/ `stdcall` | 导入函数声明可标注 |
| x64 | 单一约定（Windows x64 统一） | 无需标注 |

```cocoa
import user32.dll
cdecl function MessageBoxA(hWnd: int, text: int, caption: int, type: int): int
```

### 2.4 与 `export` 的关系

- 本编译器 `-f dll` 导出（`export fn`）→ 其他 Cocoa 程序/其他语言程序 `import` 消费
- 同一导入表机制，双向闭环

### 2.5 IL 路径：managed P/Invoke（阶段 5-3 ~ 5-5 已落地，双机制共享同一语法）

IL 路径（托管 PE 输出）消费 native DLL 走 **ImplMap/ModuleRef** 机制（ECMA-335 II.15），不产生导入表/IAT：

```cocoa
import kernel32.dll

stdcall function GetTickCount(): int
stdcall function ExitProcess(exitCode: int)

function Main()
{
    var t = GetTickCount()
    ExitProcess(42)          // 参数/返回值穿越 P/Invoke 桩
}
```

**语法规则**（与 §2.1 相同）：
- `import <dll 名>`：点号分隔的文件名，`DllName` 由 token 拼接
- `cdecl` / `stdcall` 修饰的 `function` 声明 → **外部函数声明**（允许无函数体；带函数体或缺少前置 `import` 均为诊断错误）
- 无修饰的 `function` 声明不变（普通函数，函数体必填）

**写侧机制**（自研元数据写入器）：
- extern 方法：MethodDef 的 Flags 含 PInvokeImpl(0x2000)、RVA = 0；ImplFlags = PreserveSig(0x0080)
- ModuleRef 表：每个 `import` 一行（按首见顺序去重）
- ImplMap 表：MappingFlags = 约定掩码 | CharSetAnsi(0x0002)（Winapi 0x0100 / Cdecl 0x0200 / StdCall 0x0300）；MemberForwarded 指向该方法
- **IL 签名恒用默认调用约定（首字节 0x00）**，本机约定只由 ImplMap.MappingFlags 表达

**已验证能力**（e2e，`dotnet` 运行验证）：
- 零参（GetTickCount → int 返回值）、带参（ExitProcess(int) → 退出码验证参数穿越）、int→指针（`GetModuleHandleW(0)` → LPWSTR NULL）、stdcall/cdecl 双关键字

**当前限制**（阶段 6 语言扩展前置）：
- 参数/返回类型仅限 int/bool/void（`GetStdHandle(-11)` 等 int 参数 API 可直接用）
- 字符串参数需 LPStr/UTF 编组（`byte[]` + 字符串增强后支持）；`MessageBoxA(hWnd, text, caption, type)` 待字符串编组落地

## 3. `.cod` 库引用

```cocoa
// lib.cod 由 coc build -p lib.coproj -f cod 生成
// 消费方 coproj:
[references]
../Libs/lib.cod
```

- 加载 `.cod` → 反序列化 IR → 符号表并入编译单元 → 引用解析
- 符号冲突检测（同名导出 → 错误）
- 平台不匹配 → 错误（`cod` 头含平台信息）

### 3.1 依赖传递

`.cod` 头部含**依赖清单**（.NET 程序集引用 + native 导入列表，见 `docs/项目格式规范.md` §4.1）。消费方加载 `.cod` 时：

1. 反序列化 IR 与符号表
2. 读取依赖清单
3. .NET 程序集引用 → 并入消费方引用集（IL 路径 AssemblyRef）
4. native 导入 → 合并 `import` 声明（→ 导入表）
5. 被引用的 `.cod` → 递归加载

### 3.2 与 .NET 混用

导入 `.cod` 可以编译成 .NET 程序（IL 路径），因为 IR 支持 `.NET 元数据`外部符号（`docs/IR设计.md` §2.1），cod 代码与 .NET 程序集引用在同一次编译中并存：

```
foo.cod（IR，内部可引用 .NET API）
    │ [references] 加载 + 依赖传递
    ▼
消费方编译单元 ──► IL 后端 ──► 托管 PE（.NET 程序）
```

| 消费方产物 | 结果 |
|-----------|------|
| `-f exe`（IL 路径，netcore） | .NET 托管程序（`dotnet x.exe` 运行） |
| `-f exe`（IL 路径，netfx `--dotnet-runtime net4x`） | .NET Framework 托管程序（Windows 直接运行 `x.exe`，无需 dotnet 前缀） |
| `-f dll`（IL 路径） | .NET 库，可被其他 .NET 程序引用 |
| `-f exe`（Native，纯 Cocoa 代码） | 原生 PE |
| Native + cod 含 .NET 调用 | 阶段 9 CLR Hosting |

**边界**：Cocoa 泛型是编译期特化，cod 中已特化的泛型可引用 .NET 泛型类型；.NET 运行期泛型元数据无法反向进入 IR。

## 4. .NET DLL 导入（IL 路径）

```cocoa
// 编译：coc main.co -r System.Runtime.dll
System.Console.WriteLine("hello")
System.Math.Max(10, 20)
```

### 4.1 机制

- IL 路径：`AssemblyRef` 直通（阶段 5 自研元数据写入器支持 AssemblyRef 表）
- 类型映射：`System.Xxx` → 元数据引用；Cocoa 基础类型映射到 CLR 类型
- 解析与重载：当前 Mono.Cecil 的 MetadataResolver 在阶段 5 重写为自研元数据读取

### 4.2 边界（阶段 6 范围）

| 能力 | 状态 |
|------|------|
| 静态方法调用 `call` | 阶段 6 |
| 实例方法调用 `callvirt` / 属性访问 | 阶段 6（语言扩展后） |
| 对象创建 `newobj` | 阶段 6（record/类支持后） |
| 泛型类型 | 阶段 6 |
| 异常 try/catch | 阶段 6 |

### 4.3 Native 路径的 .NET 互操作（阶段 9 可选）

- 通过 CLR Hosting API（`ICLRRuntimeHost` 等）在 Native 进程内加载 .NET 运行时并调用
- 纯 Windows 原生互操作，无第三方依赖
- 前置：阶段 6 的 native DLL 导入（Hosting API 本身就是 native API）
