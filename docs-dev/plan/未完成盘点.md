## 阶段 8 复核：22 个 ilverify 错配的基线无效（2026-09-29）

> ⚠️ **本节结论两次翻转，最终结论见下。最终状态：22 这个数字本身不可用，
> 原归因（.co 侧）大概率仍成立，需重建 B1 后重新测量。**

### 第一次误判（已推翻）

曾断言「这批错配是 C# 轨发射器自身的缺陷（局部签名类型推断 + 成员调用 token 归一化）」，
依据是 dump B1 发现 `Binder::FieldTypeOf` 的 `locals=Int32, Int32`，
而源码里 `let k = node.Child(i).Kind()`、`Node::Kind` 返回 `String`，局部量应为 String。
**该断言错误。**

反证：加了最小复现 `LocalSig_MethodCallReturningString_NotMarkedInt32`（普通类方法调用
返回 string 赋给 `let` 局部量，再与字符串比较）在**当前 HEAD 上通过**——C# 发射器的局部
签名推断并没有把 String 写成 Int32。

### 真正的根因：陈旧 B1

- 该 B1 由 commit `a46152f` 构建，产物时间 08:20:47；
- 而 `.co` 侧针对**同一批错误**的修复 `2d874d2`「类方法表起点改为按实际写入位置固定」
  提交于 08:24:08——**晚 4 分钟**。B1 不含此修复。
- `2d874d2` 的提交信息已明确写出根因链条：
  **「22 个错误集中在 Binder 的三个方法，stloc 类型错配（局部签名被写成 Int32 而实际存
  string），核心是『类方法返回类型查找落空 → 返回 "?" → 局部类型退化为 i32』」**，
  并留下具体切入点：「在 `InferTypeOfExpression` 的类方法查找里，直接断言
  `GetClassMethodName(命中行)` 是否等于目标方法名，以区分『类名匹配失败』与
  『类内方法名匹配失败』」。

即：dump 里看到的「某类读到了 Binder 的方法表」（`callvirt` 落到
`Binder::MethodReturnTypeOf` / `FieldNameOf`）正是 `2d874d2` 修的那个脆弱点，
**而非 C# 发射器的 token 归一化缺陷**。`a46152f` 的 B1 早于该修复。

### 有效基线（已重建并重测）

B1 已按当前 HEAD（`d91b94e`）用**完整语料**（无 exclude 档）重建，stamp 与 HEAD 一致，
256,000 B。ilverify 重测结果：**仍是 22 条，方法与 IL offset 分布与旧记录完全一致**。
与 `2d874d2` 提交信息「ilverify 仍 22（分布不变）」吻合。

### 22 条按症状分为 3 类（可用 ilverify 消息直接区分）

| # | 症状 | 数量 | 涉及方法 |
|---|------|------|----------|
| A | `found Int32 [expected ref 'object']` | 5 | BindClassDeclaration ×2、BindClassMethod、BindClassConstructor、EvaluatorRuntime::DoubleToString |
| B | `found ref 'string' [expected Int32]` 与反向成对出现 | 14 | InferTypeOfExpression ×2 对、FieldTypeOf、MethodReturnTypeOf、DeclWordOf、BinaryGlyphOf、UnaryGlyphOf |
| C | `found Boolean`（无 expected） | 3 | InferTypeOfExpression ×2、GetClassMethodIsStatic |

### A 类根因（已两次修正，当前结论）

`EvaluatorRuntime::DoubleToString` 签名 `String (Double)`，B1 实际 IL：

```
ldarg.0
box    0x01000005    ← TypeRef 行 5 = System.Int32
call   Convert::ToString(Object)
ret
```

`box` 指令存在（`0x8C` 是 box，不是 conv.i4），但**装箱类型是 `System.Int32`，
而栈上是 `Double`** → ilverify 报 `found Double [expected Int32]`。

调用链（已核实）：

```
EvaluatorRuntime.DoubleToString(v: f64)   src/Cocoa.Co/Cocoa.Compiler/CodeGen/EvaluatorRuntime.co:12
  → v.ToString()
  → System.Double.ToString()              src/Cocoa.SDK/System.Core/Double.co:11
  → MathSyscall.DoubleToString(this)      src/Cocoa.SDK/System.Core/Syscall/MathSyscall.co:8
                                           （syscall function DoubleToString(value: f64): string）
```

该 IL 走的是 **`EmitConversion` 的 `EmitBoxIfValueType(il, node.Expression.Type)`**
（`IlEmitter.Expressions.cs:524`），即 `v.ToString()` 被绑定成 **f64→string 的转换节点**，
而非成员调用、也不是 `BuiltinKind.DoubleToString`（后者会正确发
`call Convert::ToString(double)`，见 `IlEmitter.Expressions.cs:82`）。
转换节点的 `node.Expression.Type` 被标成了 `Int32`，故装箱类型取错。

**已推翻的两个中间结论**（留档避免重走）：

1. 「facade 成员解析按名取第一个重载、应做重载消解」——**不成立**。链路上没有重载选择：
   `Double.ToString()` 是 arity 0，且终点是 `MathSyscall.DoubleToString` 的 syscall 声明。
   曾据此写的 `Facade_OverloadPicksMatchingArityAndType_NotFirstByName` 测试已删除。
2. 「C# 发射器把 String 局部量写成 Int32」——已由 `LocalSig_MethodCallReturningString_NotMarkedInt32`
   通过证伪。

**注意**：`PrimitiveToString_BoxesCorrectType_NotInt32`（字面量局部量）与
`PrimitiveToString_OnParameter_BoxesCorrectType_NotInt32`（f64 形参）两个最小复现
在当前 HEAD 上**均通过**。即该缺陷在 C# 轨探针环境下不复现——差异来自 `.co` 轨的
`MathSyscall` syscall 链路。门禁需补在 `.co` 轨侧。

**已逐条核对为正确、故排除的路径**（避免重复排查）：

- `.coa` stdlib 签名：`System.Core.coa` 中 `System.Double` 声明为 `ToString[-@f64]`，

- `TryEmitFacadeBclCall`（`IlEmitter.Facades.cs:203-215`）：`isInstance` 判定正确，

### C 类 3 条：`ldelem.ref` 用在了 `bool[]` 元素加载上

`Binder::GetClassMethodIsStatic`（`Binder.co:1781`）：

```coco

{

```

B1 实际 IL：

```
ldarg.0 / ldfld 0x04000024        ; this._classMethodStatic : bool[]
ldarg.0 / ldfld 0x04000025        ; this._classMethodOffsets : i32[]
ldarg.1 / ldelem.i4               ; _classMethodOffsets[index]  ✅ Int32
```

护栏用例的下标是裸形参。是否与下标表达式形状有关，待验证。

### 根本性纠正：B1 的 IL 由 .co 轨产出，C# 发射器不参与

（此节纠正上一提交 5d66412 的错误框架。）

`src/Cocoa.Co/Cocoa.Compiler/CodeGen/IlDriver.co:19`：

```coco
public static function BuildDllHex(source: string): string
{
    let binder = Cocoa.CodeAnalysis.Binding.Binder.Create(source)
    binder.BindCompilationUnit()
    ...
}
```

`BuildDllHex` 接收**源码文本**，用 `.co` 轨自己的 `Binder` 绑定，再由 `.co` 轨自带的
元数据写入器（`IlMetadataBuilder.co` / `MetadataEncode.co` / `PeImage.co` /
`ManagedPeWriter.co`，全在语料内）产出 PE 字节。

bootstrap 的 `Evaluate` 只是**用 C# 轨的解释器执行**这段 `.co` 程序，
27 分钟的耗时来自解释执行，不来自 C# 发射。

**因此**：

- 22 个 ilverify 错配由 **.co 轨**（`Binder.co` 的绑定决策 + `IlMetadataBuilder.co`
  等的编码）产出。C# 轨的 `IlEmitter` 在 B1 的生成过程中**完全不参与**。
- 这彻底解释了为什么**任何 C# 轨最小复现都不可能复现这批错误**——不是复现不了，
  而是那条代码路径压根不在链路上。此前几轮反复尝试隔离复现是在错误的前提上用功。
- 也解释了 `2d874d2`（`.co` 的 `Binder.co` 修复）为何是正确切入点。
- `Compilation.Emit` 在全量语料上抛的 `KeyNotFound('usTexts: string[]')`
  是 **C# 发射器自身**的另一个独立缺陷（发生在 `IlDriver.co` 上），
  与这 22 条**无关**，只是恰好挡在前面。

**上一提交的错误**：把 `Compilation.Emit` 子集探针测到的
「无 CodeGen 时 locals = Int32,String 正确」当作「B1 的 locals 签名」来解读。
两者是**不同发射器**的输出，不能相互印证。该子集探针测的是 C# 发射器
在 `Binding/Syntax/Symbols` 上的行为，其结论仅限于此。

**修正后的正确认识**：

| 组件 | 谁产出 | 是否与 22 条有关 |
|------|--------|------------------|
| C# 轨 `IlEmitter`（`Compilation.Emit` 路径） | C# | **无关** |
| C# 轨 `Evaluator`（解释执行 .co 程序） | C# | 间接（宿主） |
| `.co` `Binder.co`（绑定决策） | .co | **是** |
| `.co` `IlMetadataBuilder.co` 等（IL/PE 编码） | .co | **是** |

**下一步应改为在 .co 轨加门禁**：`.co` 轨已有 `DescribeBoundTrees` / `DescribeSymbols`
等自省接口，且 22 条全部由它产出。门禁形态应是「用 .co 编译器编译一段语料 →
对产出做 ilverify」，而不是继续在 C# 轨找复现。

C# 发射器的 `KeyNotFound('usTexts: string[]')` 仍值得单独修（它是真实的
`Compilation.Emit` API 缺陷），但不应再占用阶段 8 的时间。

**门禁缺口**：这些缺陷只在 .co 轨自举 + 手工 ilverify 时暴露，
C# 轨探针环境看不到 `System.Convert`（引用是受控子集），无法加 C# 轨回归测试。
应在 .co 轨侧补门禁。

## 阶段 8 里程碑：B2 == B1 fixpoint 达成（2026-09-30）

**判定：字节级一致。** 这是项目对 fixpoint 的定义（沿用 `B2_Fixpoint_ViaSavedB1`
的 `Assert.Equal(b1Bytes, b2Bytes)`）。

### 达成方式：14 秒快速自举回路

新增 `Corpus_EmitAndRun_FastSelfHost`。与 bootstrap 的本质区别：

| | bootstrap `B1_Bootstrap_ReferenceEnd` | 新 `Corpus_EmitAndRun_FastSelfHost` |
|---|---|---|
| 生成 B1 的方式 | `Compilation.Evaluate`——由 C# 轨**解释器**逐条执行 `.co` 语料 | `Compilation.Emit` 产出可执行程序集，由 CLR **原生执行** |
| 耗时 | **40 分钟** | **约 15 秒** |
| 需要 B1 可运行？ | 是（下一轮要用它编译） | **否**（B1/B2 只是字节产物） |

最后一列是能达成 fixpoint 的关键：既有 22 条 ilverify 错配使 B1 本身无法运行
（`B2_Fixpoint_ViaSavedB1` 会在 `Lexer.Next()` 抛 `InvalidProgramException`），
所以「跑 B1 再编译」这条路被堵死；而快速回路里跑的是 **C# 轨发射的 runner**
（IL 有效），`.co` 编译器在其中原生执行并**产出字节**，全程不需要 B1 可加载。

### 副产品：22 条错误在 15 秒内可复现

`COCOA_SELFHOST_FULL=1` + `COCOA_RUN_ILVERIFY=1` 时，喂全量语料可在 15 秒内产出
256,000 B 的 B2 并复现**完全相同的 22 条错配、同样的 IL offset**。
即阶段 8 的错误迭代周期从 **40 分钟/轮** 降到 **15 秒/轮**。

### 前提：两个 C# 发射器修复

`.co` 语料必须能整份编译成 IL 才能走快速回路，这依赖本轮修掉的两个发射器缺陷：

1. `EmitAssignmentExpression` 缺「普通（非 byref）形参赋值」分支，
   落到 `_locals[node.Variable]` 抛 `KeyNotFoundException`。
   真实触发例是 `IlDriver.co` 的 `usTexts = ug2`（形参重绑定，C# 语义合法）。
2. opcode 表里**没有 `starg`**（ECMA-335 III.2.7.13 = `0xFE0B`）。
   补 `Define("Starg", 0xFE0B, InlineVar)`；`IsLoadInstruction` 的 default 分支
   评论里本就提到 Starg，故 `StackDelta` 自动为 -1。

实现中还踩到：赋值表达式必须留下值。首版只发 `EmitExpression; Starg`，
被 CLR 判 `InvalidProgram`——语句层会再 pop 一次，而 starg 已把值弹掉，栈下溢。
补 `Dup` 后与末尾局部变量路径（`Dup + Stloc`）语义一致。

### 比对时的坑

fast loop 喂给 `BuildDllHex` 的源码**必须与 bootstrap 的 master 逐字一致**
（含 Main 体 `BuildDllHex` + `WriteLine("B2:"+h)`）。首轮我用 `Main { return 0 }`，
被编译源码不同 → `#Strings` 堆大小不同 → 字节不等，
一度误判为「有非确定性差异」。实际首个差异出现在元数据区约 0x18F 处。

### 仍未解决

- **22 条 ilverify 错配依旧存在**（A 类 5 / B 类 14 / C 类 3）。
  fixpoint 达成**不**等于正确：它只证明「B1 能产出与自身一致的字节」，
  证明的是自举的**稳定性/确定性**，不是产物的 IL 合法性。
  这 22 条是 `.co` 轨的编码缺陷，需逐条清零（现在有 15 秒回路可快速验证）。
- `B2_Fixpoint_ViaSavedB1` 仍失败：它要求 B1 可运行，而 B1 有 22 条非法 IL。
  属**既有**失败（记录中早有），非本轮引入。快速回路已绕过该限制，
  两者可并存；待 22 条清零后旧测试应自然转绿。


- **B1 的 AssemblyRef 指向 `System.Private.CoreLib`（.NET Core 实现程序集），不是 `mscorlib`。**
  `ilverify` 若不提供 `System.Private.CoreLib` 引用，**每个方法**都报
  `FileLoadErrorGeneric`，真实错误会被完全淹没——极易误判为「所有方法都坏了」。
  正确用法：把 `Microsoft.NETCore.App\<ver>` 下的 dll 拷到被验程序集同目录，
  逐个 `-r` 传入并加 `-s System.Private.CoreLib`。
- `SelfCompileProbeTests` 里那句「ilverify 门禁」是**注释里的 aspirations**：
  代码只做了 `Assembly.LoadFile` + EntryPoint + 类型数，**从未真正调用 ilverify**。
  真实错误数此前只能靠手工跑 ilverify 得到。

这是 `.co` 轨 **codegen** 的缺陷，定位在 `Parser`/`Binder` 的 `.co` 发射路径，
不是「小输入」的边界问题，也不是 C# 轨两个后端的问题。

C# 轨发射的 runner（它 `File.ReadAllText` 读文件），**B1/B2 自身从未被喂过真实输入**；
快速回路只对它们做**字节比对**，从不让它们干活。字节相等 ≠ 能干活。

### 进一步定位：`args[0]` 的 string 元素读取（更可能，且可测）

> **本节的两条假设均已被实测推翻，见下面「真正的根因」一节。保留推理过程是为了避免后人重走。**

三条实测把范围压到很小：

1. **不传参** → `Unhandled exception. System.IndexOutOfRangeException`
   → 证明 `args` 是**真实数组**且长度正确（0 个），argv 数组的构造没问题。
2. **传垃圾参数** `ZZZ_not_source` → `B2:ERR:no functions`
3. **传合法小源码** → `B2:ERR:no functions`，与 (2) **输出完全相同**，
   且是**零诊断、零警告**、零顶层函数。

零诊断 + 零警告是关键：若 `BuildDllHex` 真拿到了可解析的源码，至少会有类型推断落空的
非致命告警（快速回路断言过 `binder warnings == 0` 是针对**全量语料**的）。
什么都不产出，说明它拿到的**输入里没有任何可解析内容**——最可能是 `args[0]`

**关于 `ERR:no functions` 本身**：它发生在 `BuildDllHex` 的
`GetTopLevelFunctionCount() < 1` 早退分支，**还没走到元数据写出**，
而 Parser/Binder 的 IL 又是干净的——所以它**不是**非法 IL 造成的。
真正的根因已定位到**语法树子节点布局不一致**（下一节）。

### `ERR:no functions` 的真根因：`VariableDeclaration` 子节点布局不一致

`.co` 轨内部对 `VariableDeclaration` 这一个节点，**存在两套互不兼容的布局约定**：

| 位置 | 角色 | 布局 |
| --- | --- | --- |
| `Binder.co:2293` | **构造**声明节点 | `[decl, name, **expr**]`——初始化器在索引 **2**，**不含 EqualsToken** |
| `Interpreter.co:205` | 消费 | `EvalExpression(stmt.Child(2), ...)`——按索引 **2** 取初始化器 |
| `IlEmitter.HasInitializer` | 消费 | 检查 `stmt.Child(2)`，`IsToken()` 为真就判定「无初始化器」 |
| **`Parser.co:887` `ParseVariableDeclaration`** | **产出** | `[let/var, name, (TypeClause)?, (**EqualsToken**)?, expr?]`——**EqualsToken 占了索引 2** |

`ParseVariableDeclaration`（Parser.co:903-908）先 `vd.Add(Match("EqualsToken"))`
再 `vd.Add(ParseExpression())`，于是 `EqualsToken` 落在索引 2、真正的表达式落到索引 3。
而**所有消费方都按索引 2 取初始化器**。

**这解释了全部现象**：

- **bootstrap 正常**：`Compilation.Evaluate` 走的是 **C# 轨的解析器**，产出的布局与消费方一致。
- **`B1 == B2` 字节级成立**：两者都由 `BuildDllHex` 在同一路径下产出。
- **B1/B2 一运行就 `ERR:no functions`**：运行时走的是 `.co` 轨**自己的** `Parser`
  （`IlDriver.BuildDllHex` → `Binder.Create` → `Parser.Create`），
  布局错位 → 初始化器读不到 → `GetTopLevelFunctionCount()` 返回 0。
- **Parser/Binder 的 IL 全部 JIT 干净**：这跟本问题无关，本问题是**语义错位**不是非法 IL。
- **零诊断、零警告**：错位后没有任何东西被判为错误，只是"什么都没解析出来"。

**修哪一边需要先定夺**（两种改法都成立，但影响面不同，**未擅自改**）：

1. 让 `ParseVariableDeclaration` **不把 EqualsToken 放进节点**（改 Parser，对齐既有消费方）；
2. 或让所有消费方改用索引 3，并让 `Binder.co:2293` 的合成节点也带上 EqualsToken（改 3+ 处）。

选 1 改动最小且与 `Binder`/`Interpreter` 现状一致，**但必须先用快速回路验证**——
不能靠 40 分钟 bootstrap 试错。

### `&` 运算符：已定位并修复 —— 非法方法体 **59 → 8**

真凶不在 `EmitBinaryOp`，而在 **`Binder.GlyphOf`**（把运算符 token 映射成字形，
`EmitBinaryOp` 与 `ApplyBinary` 都吃它的输出）：

```co
if k == "AndKeyword" || k == "AmpersandAmpersandToken" { return "&&" }
if k == "OrKeyword"  || k == "PipePipeToken"          { return "||" }
i = i + 1
}
return "?"          // ← & | ^ << >> 全落在这里
```

`& | ^ << >>` 没有字形，于是 `EmitBinaryOp` 收到 `op = "?"`，匹配不到任何分支，
**一个字节都不发** → 栈失衡 → `InvalidProgramException`。

**这也解释了上一轮的困惑**：我在 `EmitBinaryOp` 里补的 `And`/`Or`/`Xor`/`Shl`/`Shr`
分支是**死代码**——glyph 根本到不了那里。修 `GlyphOf` 后它们才真正生效。

已补：`AmpersandToken→"&"`、`PipeToken→"|"`、`HatToken→"^"`、
`ShiftLeftToken→"<<"`、`ShiftRightToken→">>"`（token 名见 `Parser.co:1497-1516`）。

| | 非法方法体 | 分组 |
| --- | --- | --- |
| 修复前 | **59**/955 | X64Assembler 29 / ManagedPeWriter 5 / PeImageBuilder 5 / MetadataEncode 4 / HexCodec 3 / IlDriver 3 / IlMetadataBuilder 3 / IlMetadataRoot 2 + 7 个各 1 |
| 修复后 | **8**/955 | IlDriver 2 + EvaluatorRuntime / IlAssembler / IlMetadataBuilder / IlMetadataRoot / Interpreter / ManagedPeWriter 各 1 |

**最可能的原因（未证实）：`StackOverflowException`。**
症状高度吻合——.NET 遇到栈溢出会**立即终止进程且不输出任何东西**（无 stderr、无结果行）。
而失败时机不固定（~1.5 min / ~14 min / ~33 min）也吻合：bootstrap 是在
**C# 轨的解释器（`Compilation.Evaluate`）里递归执行 `.co` 代码**，
`Parser.ParseBinary`（右递归）、`Binder.WalkMember`（递归下钻）、`Binder.BuildBound` 都是递归的，
其实际栈深受 GC 状态、JIT 分层、内联决策影响——**天然会时好时坏**。
那次 39m11s 的成功可能只是运气好。

#### ❌ 试过大栈线程，**没有解决问题，假设未获证实**

把 `CompileCorpusToHex()` 放进显式 `new Thread(fn, 256MB StackSize)` 跑
（并把异常显式抛出以免静默消失），结果：

- 进程**仍在约 1 分钟内静默死亡**，stderr **0 字节**，B1 未更新
- 比之前的 ~33 min **死得更快**

**所以"栈不够大"至少不是直接原因。** 可能仍需 256MB 以上的栈（即 SOE 但更深），
也可能是别的原因（原生 AV、宿主被杀、或解释器里某种循环/耗尽）。
**已撤回这个未经验证的测试改动**——不给测试基础设施留风险。

注意这里还有一个**未排除的混淆因素**：唯一那次 39m11s 的成功是**在没有大栈线程改动**时取得的。
所以"大栈线程是否有害"同样未被排除。要重试这个思路，必须先弄清它是否会改变行为。

**仍然已排除的环境原因**（都实测过）：
- 不是 CPU 饥饿：机器 12 逻辑核，6 秒采样内最忙进程仅占单核 12.5%
- 不是 OOM：测试期间 `testhost` 内存平稳 ~227 MB，系统总 15.9 GB / 空闲 4.9 GB
- `rsatest.exe` 的 CLR 崩溃事件属本机其他程序，与 testhost 无关

**下一个该做的验证**（比继续猜更有价值）：先确认"静默死亡"是否**每次都发生在同一个源码位置**——
在 `ParseBinary` / `WalkMember` / `BuildBound` 里打计数并周期性输出进度（走 `Console.Error`，
因为 stdout 被重定向后要等缓冲刷新）。有进度输出就能定位它在第几步炸，
**没有**就是纯粹的宿主/运行时层面问题。这是把"猜"变成"测"的最短路径。

#### 尝试：给 `ParseExpression` 加递归深度护栏 —— **失败，已回退**

### 更正：上一条记录的「回归信号」是**误判**

上一条记录说"改名后 bootstrap 两次都没跑完、疑似回归"。**那是错的。**

### 关键发现 2：C# 轨自己也有结构缺陷

C# 轨产物 `Cs.dll` 加载时报：

```
Could not load type 'System.Kernel32' from assembly 'Cs, Version=1.0.0.0' because
the parent does not exist.
```

即 C# 轨为 `System.Kernel32` 发了一个**父 TypeRef 不存在**的 TypeRef。
这是**独立于 `.co` 轨**的 C# 轨 bug，之前的门禁完全没覆盖到（此前只对比字节/方法体）。
**注意**：做命名空间对照时要把这条记在心上——C# 轨不是干净的基准。

### 这条门禁为什么重要

它把「两条轨行为不一致」从一句定性判断变成了**可复现的数值 + 名字差集**。
之前三轮我都在用小用例推断大规模行为并连续推错了三次
（`args[0]` 发射错 → `args[0]` 空串 → 二进制运算符缺失），
根因都是**没有在真实规模上做对照**。这条门禁正是那个缺失的对照。

本轮发现了一条**能把 `.co` 轨 codegen 的反馈周期从 40 分钟压到 14 秒**的路子，
后续所有发射器缺陷都应该用它来迭代，而不是每次跑 bootstrap：

`Corpus_EmitAndRun_FastSelfHost`（`COCOA_SLOW_PROBE=1`，约 14s）会从语料 emit 出
`%TEMP%\cocoa-fastselfhost\<guid>\FastSelfHost.dll`。这个 runner **内部就是 `.co` 轨的
`IlDriver`**，它的 Main 是：

```co
let src = System.IO.File.ReadAllText(args[0])
let h = Cocoa.CodeGen.IlDriver.BuildDllHex(src)
System.Console.WriteLine("HEX:" + h)
```

所以给它一个**任意 `.co` 源文件**，就能拿到 `.co` 轨发射器产出的 PE 字节（`HEX:` 前缀），
再 dump 该 PE 里的 IL，就能直接观察 `.co` 发射器对某个语法构造发成了什么。

用法：
```powershell
dotnet test --filter "FullyQualifiedName~Corpus_EmitAndRun_FastSelfHost"   # 取 runner
dotnet <runner>\FastSelfHost.dll mycase.co                                 # 拿 HEX
```

**踩坑**：
- runner 目录在 `%TEMP%\cocoa-fastselfhost\<guid>`，测试日志里的 `runner:` 行
  要 `-v normal`/详细日志才可见，否则得按 `LastWriteTime` 自己找最新的 dll。
- PowerShell 处理这类大 hex 与中文文件名极易出错（`Convert.ToByte` 报
  "Could not find any recognizable digits"），**用例文件名一律用 ASCII**。
- 产物的 IL 检查仍需在 .NET 9 宿主里做（`PrepareMethod` / `GetILAsByteArray`），
  PowerShell 5.1 是 .NET Framework，`Assembly.LoadFile` 加载不了 .NET 9 程序集——
  这类检查要放回 xunit 测试里做。

### 试过但回退：让 B1/B2 直接读文件

为了让 B1/B2 能吃下 596KB 语料（绕开 32KB argv 上限），试过把 master 的 Main 改成
`File.ReadAllText(args[0])`。**bootstrap 直接失败**：

```
B1 自举阻塞: ERR:[cfn=-1:m=-1:fld=?] Unresolved bcl member: File.ReadAllText tk=MemberAccessExpression
```

`.co` 轨的 BCL 成员规划（`IlDriver.co` 的 `EnsureBcl` + `typeRefNs`/`typeRefName` 行表）
**没有 `System.IO.File` 的 TypeRef**。而 `EnsureBcl` 的 `parentRow` 是**硬编码行号**
（Console=3、String=4……），源码注释自己标了「行号耦合」；TypeRef 行号还取决于
Console/String/Int32/Boolean/Char/Double/Convert 这几个条件分支的有无。
在 B1 能否正确工作都还没验证之前动这张表，风险远大于收益，故**已回退**，
保持仓库处于「bootstrap 可通过」的状态。这个改动要等 `string[]` 读取修好、
B1 能真正干活之后再做，那时才有验证手段。
