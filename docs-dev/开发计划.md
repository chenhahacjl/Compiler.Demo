## 阶段 0 — 修复 x86 Native 崩溃 ✅ 已完成（2026-08-13）

**目标**：修复 hello-x86.exe 在管道输入 "123\r\n" 时的崩溃（0xC0000005）。

**方法**：黑盒对照 —— 不靠猜测，用等价 C 程序 + 成熟编译器验证行为。

| 步骤 | 动作 |
|------|------|
| 0.1 | 安装 TinyCC + MinGW-w64（含 objdump） ✅ |
| 0.2 | 编写与 Runtime.X86 语义等价的 C 程序（input/print/字符串处理） ✅ |
| 0.3 | `objdump -d -Mintel` 对照反汇编：栈帧、栈检查、input 路径、字符串布局、调用约定、导入表 ✅ |
| 0.4 | 同输入 "123\r\n" 运行 tcc/gcc 版本，确认行为 ✅ |
| 0.5 | 修复 `src/Cocoa.Core/CodeAnalysis/Emit/Native/Runtime/Windows/X86/Runtime.X86.cs` ✅ |
| 0.6 | 回归：runx86.ps1 exit=0、stdout 完整；x64 同步验证 ✅ |

**验收标准**：hello-x86.exe 管道输入不再崩溃；x86/x64 双平台基线测试全绿 ✅。

### 阶段 0 结论（根因与修复记录）

**崩溃链**：`main → print → WriteStr(0x401530) → call [0x404094]`。IAT 槽 0x404094 被自举导入 stub
误填为 `WriteConsoleA` 的真实地址（0x766DF2F0，应为 WriteConsoleW 0x766DF300），跳到错误入口执行
垃圾代码，最终落入 kernel32 导出名字表（PAGE_READONLY 数据页）→ 取指访问违规 0xC0000005。

**根因**：`ImportResolverStubEmitterX86.AnsiWords()` 只用导出名的**前 8 字节**生成匹配模板，
名字超过 8 字符时第 9 字节起未进入模板。kernel32 名字表按字母序扫描，前 8 字节相同的变体先被命中：
`GetFileType→GetFileTime`、`ReadConsoleW→ReadConsoleA`、`WriteConsoleW→WriteConsoleA`。
`WriteFile` 恰好正确——它是 `WriteFileEx`/`WriteFileGather` 的最短前缀，字母序最前先被扫到。
（x64 版同模式缺陷，16 字节阈值，当前最长导入名 15 字符侥幸未触发。）

**修复**（2026-08-13，双平台对称）：
- `src/Cocoa.Core/CodeAnalysis/Emit/Native/Runtime/Windows/X86/ImportResolverStubEmitterX86.cs` — `AnsiWords`
  改为按名字实际长度动态生成全部 dword 模板，Emit 循环逐块比较，掩码屏蔽跨界读入的相邻名字字节
- `src/Cocoa.Core/CodeAnalysis/Emit/Native/Runtime/Windows/X64/ImportResolverStubEmitter.cs` — 相同修复（qword 粒度）

**验证**：
- hello-x86/hello-x64 控制台模式正常输出、exit=0；`debughost6` 确认 IAT 槽全部与导出表精确一致
- `ImportResolverTests` 17 个回归测试（模板全长度覆盖 + 前缀变体扫描模拟），4877 测试全绿

## 阶段 1-3 — IR 层

**目标**：在绑定树（Lowerer 输出）与 IAssembler 之间插入统一 IR，使 x86/x64 后端共享同一中间表示。

### 阶段 1：IR 设计

- 三地址码（每个指令最多一个目的寄存器 + 两个操作数）
- 虚拟寄存器（无限，由后端分配物理寄存器/栈槽）
- 逻辑/比较直接写入目的寄存器（`cmp v_dst, v_a, v_b`）
- IR 指令集覆盖：常量加载、mov、算术/逻辑/比较、分支/标签、call、栈操作、内存读写（字符串/数组）

**阶段 1 已完成（2026-08-13）**：`Emit/IR/` 骨架（IrVirtualRegister 分配器/IrOpCode/IrInstruction/IrCond/IrProgram/IrPrinter）

### 阶段 2：Native 后端 IR 化

### 阶段 4 结论（关键修复记录）

运行时 IR 化过程中暴露并修复了 10 个编译器后端缺陷（部分为 IR 化前就潜伏的既有 bug）：

| # | 根因 | 修复 |
|---|------|------|
| 1 | SSA 循环内变量重绑定（`tail = nextTail`）不生成复制指令——IR 线性复用导致每次迭代读初始槽 | 循环内改显式 `Mov(tail, nextTail)` 回写（BuildInt/CopyChars/ParseInt/StrEquals） |
| 2 | 分支内重绑定 + 分支外使用（`tail = signTail`）：无符号路径槽未初始化读垃圾 | φ 展开：两条路径统一赋值 `copyTail`（BuildInt） |
| 3 | `LeaSlot` 缓冲越界：buf 槽距返回地址 0x28 而 BuildInt 需 buf+44，写穿返回地址 | frame 预留 0x80 缓冲 + LeaSlot 指向帧底（x64/x86 对称） |
| 4 | x86 `EmitSetArg` 对第 3 参数直接跳过（`ordinal>=2` return），CopyChars 的 count 丢失 | 第 3 参数发射到 ESI（与 EmitInitRegArg 一致） |
| 5 | `EmitSysCall` 第 5 参数固定写 0，Input 的 writtenAddr 丢失 | 第 5 参数从 `_sysArgs[4]` 取值 |
| 6 | `EmitUdiv` 缺除零检查（Idiv 有）→ 硬件除零异常 | 补 `cmp ecx,0; je DivByZero` |
| 7 | 16 位 `Load` 用 `mov ax`（66 8B）不清高位，字符比较被高位垃圾污染 | 16 位加载改 `movzx`（0F B7） |
| 8 | DivByZero/StackOverflow 由 jcc（不压栈）进入，入口 rsp 与 call 进入差 8，函数内对齐错 → 调 kernel32 时 KERNELBASE movdqa 崩 | 这两个函数帧大小 ≡8（先对齐 ≡0 再 +8，仅按函数名判定） |
| 9 | Input 的 `LeaSlot(writtenAddr)` 在 console 分支内赋值，notConsole 分支用未初始化槽 | LeaSlot 移到 GetFileType 判断前的公共路径 |
| 10 | 探索过程中的教训：构建失败时 dotnet test 静默用旧 dll，产生"全崩"假象 | 修改后端后先显式 `dotnet build` 确认编译通过再跑测试 |

调试工具链：procdump（Sysinternals）抓崩溃 dump + cdb（WinDbg 包 `amd64\cdb.exe`）分析/软件断点二分。

**运行时结论（5-4 踩坑记录，勿回退）**：
1. extern 方法的 IL 签名必须用默认调用约定（首字节 0x00）；本机约定（cdecl/stdcall）只由 ImplMap 的 MappingFlags 表达。写 0x01/0x02 会 `TypeLoadException: The signature is incorrect.`
2. extern 方法 MethodDef 行的 ImplFlags 必须写 `PreserveSig`（0x0080），否则 JIT 桩对返回值处理异常（int 返回恒得 0）。
3. MethodDef 行字段顺序为 RVA(4) + ImplFlags(2) + Flags(2)：PInvokeImpl(0x2000) 属 Flags；ImplFlags 与 Flags 不可混淆。
